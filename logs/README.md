# Журналы

`logs/` хранит операционные факты этой Product Unit.

## Индекс

1. `changes.md` — изменения артефактов.
2. `decisions.md` — решения владельца.
3. `quality.md` — проверки и результаты.
4. `releases.md` — факты выпуска после отдельного решения.
5. `risks.md` — риски и блокеры.
6. `sessions.md` — сессии и свидетельства интервью.
7. `terminology.md` — изменения терминов.

Первая реальная работа создаёт первую операционную запись. Стартовая поставка не содержит синтетических решений владельца или фиктивных свидетельств интервью.

## Поставочная чистота и рабочее состояние

Пустые обязательные журналы являются свойством исходной поставки Harness, минимального канонического starter-сценария и восстановления отсутствующего файла.

После начала работы допустимы и ожидаемы записи:

1. свидетельств интервью;
2. решений владельца и SoT;
3. качества и рисков;
4. сессий и изменений;
5. продуктовой приёмки.

Рабочая Product Unit проверяется по структуре, связям и валидности записей, а не по пустоте журналов. `bp_init.py` создаёт отсутствующий журнал с чистым заголовком, но сохраняет существующий файл и все операционные записи без очистки или перезаписи.

## Формат свидетельств

`changes.md`, `quality.md`, `risks.md`, `sessions.md` и `decisions.md` используют канонические runtime-ссылки `codexlog:.codex/<actual-log-file>#lines=<start>-<end>`. Локальная проверка подтверждает путь внутри `.codex/`, существование файла и конечный корректный диапазон. Тип записи, `DECISION_KIND` и `SOURCE_KIND` задают ожидаемый класс источника.

Одна ссылка доказывает одно событие:

1. `owner_decision` — фактическая реплика разрешения владельца;
2. `change_result` или `implementation_result` — фактическое изменение либо завершённый результат;
3. `verification_result` или `terminal_verification` — итог проверки без подмены промежуточной ошибкой;
4. `owner_acceptance` — фактическая реплика продуктовой приёмки;
5. `owner_answer` или `owner_confirmation` — фактически полученное интервью.

Одна ссылка не обязана доказывать разные события. Локальная проверка опирается на locator и схему записи; произвольная проза их не заменяет.

Новая операционная запись в `changes.md`, `quality.md` и `risks.md` использует единый каркас:

```text
RECORD_ID: <типизированный ID>
PLAN_ID: <PLAN-ID | none>
DATE: <YYYY-MM-DD>
SUMMARY: <краткий факт>
SOURCE_REF: codexlog:.codex/<actual-log-file>#<ровно один selector>
```

Специализированные поля добавляются после каркаса. Записи разделяются пустой строкой; один machine key встречается в блоке ровно один раз.

`sessions.md` хранит типизированный `interview_evidence` по `templates/session-record.md`; `decisions.md` хранит `owner_decision` и `product_acceptance` по `templates/decision-record.md`. Каждый их операционный блок начинается с `RECORD_TYPE`. `SOURCE_REF` обязан разрешаться в существующий локальный диапазон.
