# Проверка работы

Целевой артефакт: `logs/quality.md`.
Шаблон или формат: `templates/quality-record.md`.
Способ записи: дозапись.

Проверки выполняются на разрешённой рабочей копии Product Unit. Если исходная поверхность защищена внешним маршрутом, используется временная копия.

```bash
python3 -m py_compile tools/bp_init.py tools/bp_check.py tools/bp_clean.py
python3 tools/bp_check.py --repo .
```

К ним добавляются product unit tests и product smoke, заданные active PLAN или продуктовым README.

## Граница решения владельца

Technical PASS является свидетельством, но не означает:

1. продуктовую приёмку;
2. готовность к выпуску;
3. разрешение tag;
4. разрешение GitHub-действий.

Продуктовая приёмка требует отдельной записи `RECORD_TYPE: product_acceptance` с ID `PA-*` и точной ссылкой на ответ владельца.

## Проверка active PLAN

Проверка подтверждает текущее состояние:

1. active PLAN существует в количестве `0..1`;
2. фаза соответствует текущей работе;
3. `ALLOWED_SURFACES` не расширяет внешнюю границу;
4. обязательные IE, implementation decision и product acceptance существуют, когда их требует фаза;
5. product identity согласована между brief, PLAN и root README;
6. для product-bearing состояния пройдены product unit tests и product smoke.

Историческая реконструкция последовательности изменений не выполняется.

## Проверка защищённых поверхностей

Канонический реестр находится в `SYSTEM.md`. В `product-work` системные поверхности не разрешаются, кроме точных `AGENTS.md::SOT_MODE` и `AGENTS.md::SOT_GITHUB_REPOSITORY`, если один transition checkpoint уже разрешён владельцем и active PLAN.

Запрещённое изменение или дефект Harness останавливает работу. Агент выводит:

```text
HARNESS_BLOCKER: <краткое описание>
```

после чего не проектирует исправление, не запрашивает `system-editing PLAN`, не предлагает повторное исполнение, не создаёт Harness research и не управляет Workspace.

## Проверка DoD

Verifier:

1. связывает DoD с текущим `ROAD -> BACK -> PLAN`;
2. выполняет проверки active PLAN;
3. добавляет product unit tests и product smoke для реализованного продукта;
4. фиксирует результат и непроверенные области в `logs/quality.md`;
5. отдельно указывает, что технический PASS не является продуктовой приёмкой.

## Одноразовые артефакты

Перед clean-exit проверяются:

1. `__pycache__/` и `*.pyc`;
2. временные файлы;
3. наличие `research/README.md` и `research/archives/README.md`;
4. отсутствие `docs/research/` как рабочего исследовательского слоя.

## README и пользовательская граница

После появления продуктового кода root `README.md` содержит:

1. назначение и ценность;
2. пользователя;
3. запуск;
4. основные команды;
5. хранение данных;
6. ограничения;
7. проверки.

`docs/user/` не содержит внутренних `ROAD`, `BACK`, `PLAN` или динамического статуса Harness. Публичное описание SoT configuration допустимо. Для GUI-продукта технический PASS не заменяет визуальную проверку: если окно не проверено, используется статус `ready-for-owner-check`.
