# Подготовка репозитория GitHub

## Назначение

`sot_github` означает, что принятая базовая версия находится в ветви по умолчанию ожидаемого репозитория GitHub, а локальный Git используется как рабочая копия. Режим сам по себе не разрешает push, pull request, merge, tag или GitHub Release.

## Профили аккаунтов и роли

Поддерживаются три профиля:

1. Одна учётная запись — все роли может выполнять один пользователь; независимое GitHub approval может отсутствовать, поэтому решение по exact head сохраняется в журнале решений и свидетельствах.
2. Владелец + агент — автор и исполнитель могут работать из отдельной учётной записи, а владелец утверждает exact head; это рекомендуемый, но не обязательный профиль.
3. Команда — permissions, число approvals и CODEOWNERS определяет политика конкретного репозитория.

Смысловые роли: автор изменения, утверждающий, исполнитель слияния и публикатор выпуска. BytePress не управляет пользователями или permissions и не требует отдельной учётной записи агента.

## Конфигурация Product Unit

В `AGENTS.md` хранится `SOT_MODE`. Только для `sot_github` рядом обязательно одно поле `SOT_GITHUB_REPOSITORY` со значением `owner/repository`. URL, имя remote, ветви по умолчанию и выпуска, учётная запись и credentials в конфигурации не хранятся.

Remote всегда один и называется `origin`. Его URL должен указывать на ту же repository identity и использовать HTTPS GitHub, стандартную SSH-форму, SSH alias либо `ssh://`. Локальный путь, `file://` и HTTP credentials запрещены.

## Профили веток

Выберите один профиль, соответствующий продукту:

1. Минимальный профиль — одна ветвь по умолчанию и короткоживущие рабочие ветки. Он допустим для простого продукта, одного пользователя и выпуска без отдельной стабильной ветви.
2. Выпускной профиль — ветвь разработки по умолчанию и отдельная стабильная выпускная ветвь. Он используется только тогда, когда продукту действительно нужна отдельная выпускная линия.

`sot_github` не требует имён `develop` и `main`: конкретные имена веток задаёт политика репозитория. Проект BytePress использует `develop/main`, но это модель развёртывания проекта, а не core contract. Pull request, approvals и rulesets настраиваются согласно выбранному профилю.

## Подготовка репозитория

1. Создайте проверяемую резервную копию заполненного репозитория: refs, tags, настройки и release metadata; выполните независимую проверку восстановления.
2. Назначьте профиль учётных записей, смысловые роли и минимальные permissions без bypass actors.
3. Выберите минимальный или выпускной профиль и задайте конкретные имена веток в политике репозитория.
4. Используйте короткоживущие topic branches; release и hotfix branches применяйте только при выпускном профиле и в отдельных выпускных маршрутах.
5. Защитите ветви выбранного профиля от direct push, удаления и force-push; настройте pull request и закрытие обсуждений согласно его политике.
6. Для одного account допустимы `0` required approvals; для разделённых ролей обычно требуется approval текущего head; командная policy может быть строже.
7. Для обычных изменений используйте squash, для release/hotfix — merge method, установленный политикой ветви. Required status checks не являются обязательной частью core `0.5.0`.
8. Включайте автоматическое удаление рабочей ветви только как часть проверенной merge policy.

Approval относится к exact current head SHA. Новый push требует нового approval. После действующего approval merge может выполнить любой permitted executor; исполнитель слияния не обязан совпадать с утверждающим. Tag и GitHub Release требуют отдельных решений владельца.

## Внешняя предварительная проверка

До перехода внешний preflight:

1. проверяет operating identity, authentication, access и repository identity без вывода secrets;
2. получает ветвь по умолчанию из GitHub metadata;
3. добавляет или проверяет единственный `origin`;
4. выполняет отдельно разрешённый fetch;
5. обновляет локальную symbolic ref `origin/HEAD` и проверяет её target ref.

Для SSH alias preflight отдельно доказывает, что alias ведёт на GitHub. Эти действия не выполняются `bp_check.py`.

## Локальная проверка

После preflight `bp_check.py` проверяет только подготовленное локальное состояние: конфигурацию, корень репозитория, чистое дерево, `origin`, URL identity, upstream, локальные remote refs, `origin/HEAD` и допустимую divergence. Checker не использует сеть и ничего не исправляет автоматически.

## Заполненный репозиторий и переходы

Не присоединяйте независимую локальную историю к заполненному репозиторию автоматически. Начинайте рабочую ветку от remote-derived baseline, переносите только проверенный файловый payload и сохраняйте опубликованную историю, если отдельное решение владельца не устанавливает иной destructive route.

Переход выполняется только составным маршрутом с отдельной проверкой каждого checkpoint:

```text
sot_files -> sot_git -> sot_github
```

Обратные переходы не входят в `0.5.0`. Нормативные правила находятся в [../../sops/sot.md](../../sops/sot.md).
